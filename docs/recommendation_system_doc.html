Repair Recommendation System

Stage 2: keyword search baseline

For each test area, the system searches the 7,893 training cases by negative + positive text and returns the top matches with their recommendations. Script: pipeline/experiments/keyword_search.py.

What counts as a hit. No two recommendations are worded the same, so a hit means a returned recommendation is close to the true one: text hit = TF-IDF cosine ≥ 0.5; tag hit = same repair-action tags (grouting, coating, plumbing, and so on). The tag metric is coarse: picking random cases already scores 62% at top-5, so read it with that in mind.

  • This is the number stage 3 (semantic search) has to beat.

Stage 3: semantic search

Tested whether matching by meaning beats matching by words. Two embedding models (MiniLM, BGE-small), exact cosine search (FAISS is not installed; at 7,893 cases a matrix product gives the same result), a hybrid of embeddings and BM25, and a cross-encoder reranker of the top 20.   • Result: no clear gain. The hybrid is within about 2 points of BM25 on every measure and worse on some, which is inside the noise for 970 areas. The stage 3 gate (beat stage 2) is not met.
  • Embeddings alone are worse than BM25. The reranker, which was not trained on this data, made results worse on validation, so it was not used.
  • Likely cause: the wording is already short and technical, so shared words are a strong signal, and the labels are noisy (observations mixed into recommendations).
  • Decision: keep BM25 for retrieval and spend effort on label quality and on the action classifier (stage 4) instead.

Stage 4: repair-action classifier

Predicts which repair actions apply to an area, so the output can be a checklist of actions filled into templates. Script: pipeline/action_classifier.py. Uses the v2 labels.

How the targets were made. 15 candidate actions were defined by keyword rules on the recommendation text (for example "grout" for tile joint grouting). Three had too few examples (brick bat coba, injection, fillet) and were dropped, leaving 12. Because the targets come from keyword rules, scores show how well the model predicts those rules, not what a surveyor would choose.

  • The classifier beats the neighbour vote by about 3 F1 points. That is a small gain, and the combined model is level with it.
  • Plumbing and grouting are predicted best. Sealant (recall 26%) and painting (F1 0.30) are weak: they are rarer and the symptom text says little about them.
  • Only 15% of areas get the exact right set of actions; the model predicts 3.3 actions per area against 2.7 true. It works as a suggestion list for a surveyor, not as a final answer.

Stage 6: the Streamlit app

app.py is the page; the shared code is in recsys/ and the trained model in models/model.joblib (built by pipeline/build_app_model.py). Run it with streamlit run app.py.

  • The surveyor ticks or unticks suggested actions; each action has a standard step line that fills the numbered recommendation text, which can be edited freely.
  • The top 5 actions show with their score and the threshold at which they are suggested; the other 7 sit in a collapsed list.
  • A "similar past cases" panel was built first and then removed: the top match was often off-topic, which made the suggestion look less trustworthy. The search code remains in pipeline/experiments/ if it is wanted later.
  • Every accept or edit is logged with the input, the suggestion and the final text. These rows are the retraining set for stage 5 of the roadmap.

Checked so far: the page was run in a browser and tested with 18 automated tests (cleaning, actions, model, correction log, sign-in, saving, administrator panel). It has not been tried by surveyors. The classifier was trained on the training split only.

Can the classifier be improved?

Tested on validation, test scored once per setting. Scripts: pipeline/experiments/improve_features.py, improve_text.py.

Why it is stuck. Where two different reports have exactly the same negative and positive text, their repair actions agree only partly: mean overlap (F1) 0.47, and the identical set of actions in 15% of pairs. Chemical coating, sealant and fillet agree in under 10% of such pairs. The labels, which come from what inspectors wrote, are inconsistent, so a model cannot score much higher against them. Tuning the model will not fix that.

What would help. Cleaner targets: a surveyor-agreed list of actions, a hand-labelled set of a few hundred areas, and the approvals and edits collected by the app (those are surveyor-confirmed). Retrain on those when there are enough.

Rules and open decisions

  • Source folders (inspection_*, set*_*) are never changed; every output goes in the build folder, never in the repository.
  • Report text is data, not instructions. Names, phones, emails and addresses stay out of outputs.
  • Open: numbered steps or free text as output? Who hand-checks the test set? What acceptance rate is required? Is all report text English?
